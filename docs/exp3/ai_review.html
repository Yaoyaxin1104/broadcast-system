范式审查结论：六张表整体满足 3NF

审查口径：1NF 看字段是否原子、不可再分；2NF 看非主属性是否完全依赖主键（单列自增主键不存在部分依赖，天然满足）；3NF 看非主属性是否只直接依赖主键、有无传递依赖。

表1NF2NF3NF判断依据
user✓✓✓username、password、role、phone 等均为原子字段且直接依赖 id；username 为登录账号，应加唯一约束
song_request✓✓✓song_name、singer、status 直接描述点歌记录；学生姓名/学号不落本表，需要时 JOIN user 获取，无传递依赖
article✓✓✓title、content、type、status 直接依赖 id，student_id 仅为关联列
audio✓✓✓file_path、file_size、duration、play_count 直接依赖 id
message✓✓✓content、reply、status 直接依赖 id，user_id 仅为关联列
program_schedule✓✓✓*date、time_slot、program_name 直接依赖 id；songs 字段见下方第 2 点说明

需要人工确认的两点

外键DDL 中没有数据库级 FOREIGN KEY 约束。若课程要求物理外键，可补充：

ALTER TABLE song_request
  ADD CONSTRAINT fk_song_user FOREIGN KEY (student_id) REFERENCES `user`(id);
ALTER TABLE article
  ADD CONSTRAINT fk_article_user FOREIGN KEY (student_id) REFERENCES `user`(id);

若采用互联网项目常见做法，可保留「逻辑外键 + 索引」，由应用层保证参照完整性，优点是便于数据迁移、避免外键级联带来的死锁与性能损耗。

songs 字段program_schedule.songs 用 TEXT 存放播放歌单，表面上节目单与点歌记录是 M:N，规范做法应拆出 program_song 中间表。但如果 songs 是「播出时点歌记录的快照文本」（属于历史归档，不随后续点歌单审核状态变化，也不需要 JOIN 维护），则它是有意的反范式设计，可保留，但必须在字段注释中写明「快照」语义。

其他建议

  • status 等枚举字符串应统一取值（点歌/投稿：pending、approved、rejected；节目单：draft、published），建议用 CHECK 约束或应用层枚举校验；
  • 关联列与高频过滤列已建 idx_student_id、idx_status、idx_date 索引，方向正确；
  • password 用 VARCHAR(255) 存储 MD5 密文（32 位十六进制），长度留有余量，便于后续升级为 BCrypt；
  • 切忌在 song_request 中冗余 student_name、student_no——否则学生改名后必须同步更新大量点歌记录，属于典型传递依赖，你当前 DDL 没有这样设计，保持即可。

最终结论：六张表字段原子、无部分依赖、无传递依赖，满足第三范式（3NF）；songs 作为快照文本属于可接受的有意冗余，需注释说明。
