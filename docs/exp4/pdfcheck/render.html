步骤6：实现登录接口

新增登录控制器与登录业务类，业务方法按七步实现：

接收账号密码参数，做基本格式校验。

构造一个未认证的认证请求对象，把账号密码装进去。

调用认证管理器完成认证，框架会自动调用步骤 4 编写的用户详情服务。

从认证结果中取出用户详情对象，此时它已装配好角色与权限集合。

把用户详情对象以用户 ID 为键写入 Redis，过期时间与令牌有效期保持一致。

签发令牌，载荷中只放用户 ID。

组装响应：令牌字符串、有效期秒数，以及供前端使用的用户信息（账号、姓名、角色、权限标识列表）。

注意：认证失败时要统一转成「账号或密码错误」，不要分别提示「账号不存在」和「密码错误」，否则提示差异会被用来探测账号是否存在。

步骤7：实现 JWT 认证过滤器

新建过滤器类继承 OncePerRequestFilter，重写 doFilterInternal 方法，按八步实现：从请求头取出令牌（兼容带前缀与不带前缀两种写法）、无令牌直接放行、校验令牌签名与有效期、解析出用户 ID、用该 ID 从 Redis 取回用户详情、缓存中不存在则放行、二次校验账号状态、构造已认证的认证对象写入安全上下文、放行请求。

两个关键点：第一，认证失败时不要自己抛异常，也不要自己写 401 响应，而应直接放行，由授权环节统一处理；第二，判断「本次请求是否已处理过」时不能只看认证对象是否为空，因为过滤器链前段的匿名身份过滤器已经放入了一个匿名认证对象，正确做法是显式排除匿名身份。

步骤8：实现退出登录

新增退出接口，按三步实现：从安全上下文取出当前已认证的用户信息、取出用户 ID 并按与登录时完全一致的规则拼出缓存键并删除、清空安全上下文后返回成功。

因为过滤器每次都从 Redis 取用户信息，所以缓存被删除后，该令牌即便签名有效、时间未到，也再取不到身份信息，等同于立即失效。

步骤9：设计菜单表、菜单树与角色菜单授权

设计 menu 菜单表与 role_menu 角色菜单关联表。menu 表用 menu_type 字段区分目录 M、菜单 C、按钮 F 三类数据，权限标识按「模块:操作」命名，例如 song:audit、article:add；角色与菜单通过 role_menu 多对多关联。

菜单树采用两次遍历加映射表构建：第一次遍历把全部节点放入以菜单 ID 为键的映射表，第二次遍历为每个节点查找父节点并挂载、同时收集根节点。整体时间复杂度为 O(n)，既避免递归反复遍历列表，也避免层级过深时递归栈溢出。

角色菜单授权：角色列表接口返回各角色及其已选菜单；保存授权时在一个事务内先删除该角色的旧关联，再批量插入新关联，并自动补全所选菜单的父级目录，避免出现「能打开页面但上级目录不可见」。

步骤1：实现权限判断服务

新建权限判断服务类，注册为名为 ss 的 Bean，对外提供四个方法：判断是否拥有指定权限、判断是否拥有任意权限、判断是否拥有指定角色、判断是否为超级管理员。

步骤2：实现自定义权限管理器

新建权限管理器类，实现 AuthorizationManager 接口，泛型参数取请求授权上下文，表示基于请求的授权判断。判断过程分四层：

从请求上下文取出请求对象，得到请求方法与请求路径，并取出当前认证信息。

若认证信息为空、未通过认证，或主体是匿名用户，返回拒绝。

若当前用户是超级管理员，直接返回通过，不再逐条比对权限。

根据请求方法与路径解析出该请求所需的权限标识；若该路径没有配置权限要求，返回通过；否则调用权限判断服务比对，命中返回通过，未命中返回拒绝并记录告警日志。

路径与权限的对应关系建议集中在一处常量或数据库中维护，便于审阅「哪些接口受保护」。
