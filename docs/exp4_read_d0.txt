步骤4：编写用户详情服务与用户详情模型

用户详情服务实现 UserDetailsService 接口，重写 loadUserByUsername 方法，按六步完成：按登录账号查询用户（过滤逻辑删除的数据）、判断账号是否存在、判断账号是否被禁用、查询该用户的角色编码集合、判断是否为超级管理员（是则权限集合直接放入通配符，否则按用户 ID 查询权限标识集合）、装配成用户详情对象返回。

用户详情模型实现 UserDetails 接口，至少包含六个部分：用户 ID、登录账号、密码、账号状态、角色编码集合、权限标识集合。

两个必须注意的点：第一，权限为空时要返回空集合而不是空对象，避免后续比对时层层判空；第二，这个类作为缓存对象必须提供无参构造方法，反序列化时会先创建空对象再逐字段赋值。

步骤5：编写安全配置类

新建安全配置类，注册 SecurityFilterChain 类型的 Bean（Spring Security 6 中配置适配器基类已被移除），并按表中逐项完成设置。

| 配置项 | 设置要求 | 说明 |
| --- | --- | --- |
| 跨站请求伪造防护 | 关闭 | 前后端分离项目用令牌认证，不依赖会话 |
| 表单登录 | 关闭 | 不关闭时未认证请求会被重定向到登录页 |
| HTTP 基础认证 | 关闭 | 同上，避免弹出浏览器原生登录框 |
| 方法级安全注解 | 开启 | 不开启时权限注解会静默失效，不报错也不警告 |
| 框架自带退出接口 | 关闭 | 自带接口行为固定，需自行实现退出逻辑 |
| 跨域配置 | 迁移到此处 | 由安全框架统一接管跨域 |
| 预检请求 | 放行 OPTIONS 方法 | 预检请求不携带令牌，拦截会导致跨域失败 |
| 白名单 | 放行登录、注册、健康检查、错误页转发路径 | 否则会出现「想登录但登录接口也被拦」 |
| 其余请求 | 要求已认证 | 白名单放行、其余全拦 |
| 密码编码器 | 注册 BCrypt | 认证过程中框架会自动调用 |
| JWT 过滤器 | 注册并置于用户名密码认证过滤器之前 | 顺序错误会导致后续授权环节读不到身份 |

同时注册一个 AuthenticationManager 的 Bean 供登录接口调用。

步骤6：实现登录接口

新增登录控制器与登录业务类，业务方法按七步实现：

接收账号密码参数，做基本格式校验。

构造一个未认证的认证请求对象，把账号密码装进去。

调用认证管理器完成认证，框架会自动调用步骤 4 编写的用户详情服务。

从认证结果中取出用户详情对象，此时它已装配好角色与权限集合。

把用户详情对象以用户 ID 为键写入 Redis，过期时间与令牌有效期保持一致。

签发令牌，载荷中只放用户 ID。

组装响应：令牌字符串、有效期秒数，以及供前端使用的用户信息（账号、姓名、角色、权限标识列表）。

注意：认证失败时要统一转成「账号或密码错误」，不要分别提示「账号不存在」和「密码错误」，否则提示差异会被用来探测账号是否存在。

截图：（Apifox 调用登录接口，成功返回令牌）

步骤7：实现 JWT 认证过滤器

新建过滤器类继承 OncePerRequestFilter，重写 doFilterInternal 方法，按八步实现：从请求头取出令牌（兼容带前缀与不带前缀两种写法）、无令牌直接放行、校验令牌签名与有效期、解析出用户 ID、用该 ID 从 Redis 取回用户详情、缓存中不存在则放行、二次校验账号状态、构造已认证的认证对象写入安全上下文、放行请求。

两个关键点：第一，认证失败时不要自己抛异常，也不要自己写 401 响应，而应直接放行，由授权环节统一处理；第二，判断「本次请求是否已处理过」时不能只看认证对象是否为空，因为过滤器链前段的匿名身份过滤器已经放入了一个匿名认证对象，正确做法是显式排除匿名身份。

截图：（带令牌访问「当前用户信息」接口，成功返回）

步骤8：实现退出登录

新增退出接口，按三步实现：从安全上下文取出当前已认证的用户信息、取出用户 ID 并按与登录时完全一致的规则拼出缓存键并删除、清空安全上下文后返回成功。

因为过滤器每次都从 Redis 取用户信息，所以缓存被删除后，该令牌即便签名有效、时间未到，也再取不到身份信息，等同于立即失效。

截图：（退出后用原令牌访问受保护接口，返回 401）

任务二：实现授权拦截（401 与 403）

步骤1：实现权限判断服务

新建权限判断服务类，注册为名为 ss 的 Bean，对外提供四个方法：判断是否拥有指定权限、判断是否拥有任意权限、判断是否拥有指定角色、判断是否为超级管理员。

判断逻辑分三步：从安全上下文中取出当前登录用户，取不到或权限集合为空则直接返回不通过；权限集合中含有通配符则说明是超级管理员，直接返回通过；否则判断权限集合是否包含目标权限标识。

路径级授权与后面的方法注解必须共用这一处逻辑，否则规则演进时两处会不一致。

截图：（权限判断服务类）

步骤2：实现自定义权限管理器

新建权限管理器类，实现 AuthorizationManager 接口，泛型参数取请求授权上下文，表示基于请求的授权判断。判断过程分四层：

从请求上下文取出请求对象，得到请求方法与请求路径，并取出当前认证信息。

若认证信息为空、未通过认证，或主体是匿名用户，返回拒绝。

若当前用户是超级管理员，直接返回通过，不再逐条比对权限。

根据请求方法与路径解析出该请求所需的权限标识；若该路径没有配置权限要求，返回通过；否则调用权限判断服务比对，命中返回通过，未命中返回拒绝并记录告警日志。

路径与权限的对应关系建议集中在一处常量或数据库中维护，便于审阅「哪些接口受保护」。

截图：（权限管理器类）

步骤3：实现两个异常处理器

新建 handler 包，在其中创建两个处理器，均使用组件注解注册。

无权限异常处理器实现 AccessDeniedHandler 接口，重写 handle 方法：设置响应状态码为 403，设置响应内容类型与字符编码（避免中文乱码），把统一的失败响应对象序列化为 JSON 写入响应体。

认证异常处理器实现 AuthenticationEntryPoint 接口，重写 commence 方法：设置响应状态码为 401，其余处理同上。

两个对照关系如下。

| 对比项 | 认证异常处理器 | 无权限异常处理器 |
| --- | --- | --- |
| 处理场景 | 未登录或凭证无效 | 已登录但权限不足 |
| 实现接口 | AuthenticationEntryPoint | AccessDeniedHandler |
| 重写方法 | commence | handle |
| HTTP 状态码 | 401 | 403 |

两个处理器中都不要抛出异常，也不要继续调用过滤器链，否则响应会被重复写入。

截图：（无令牌访问受控接口返回 401；读者账号调用管理员接口返回 403）

步骤4：替换方法级权限注解

把原有 7 处「仅管理员」的判断逐一替换为具体权限注解。

| 原接口 | 原有判断 | 替换为 |
| --- | --- | --- |
| 查询用户列表 | 仅管理员 | 要求 user:list 权限 |
| 查询用户详情 | 仅管理员 | 要求 user:query 权限 |
| 新增用户 | 仅管理员 | 要求 user:add 权限 |
| 修改用户资料 | 仅管理员 | 要求 user:edit 权限 |
| 启用或禁用账号 | 仅管理员 | 要求 user:status 权限 |
| 重置密码 | 仅管理员 | 要求 user:resetPwd 权限 |
| 删除用户 | 仅管理员 | 要求 user:delete 权限 |

前置条件：安全配置类中必须已开启方法级安全注解，否则这些注解会静默失效，既不报错也不警告，现象是路径级拦截正常但注解完全不起作用。
